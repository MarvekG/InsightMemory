# 产品总览

[返回 README](../README.zh-cn.md)

这份文档解释 InsightMemory 要解决什么问题、它和常见 memory 方案有什么本质区别，以及它更适合哪些 AI 场景。

## 项目亮点

如果你想找的不是“又一个能搜相似文本的 RAG 组件”，而是一套真正能让 AI 应用越用越懂你、越跑越有上下文、
越回答越有依据的长期记忆层，那 InsightMemory 的核心价值大概可以概括为这几件事：

- **它记住的不是文字，而是对象**：不是把一切都丢进统一文本池，而是先判断“这条信息到底属于谁”，再围绕稳定主体沉淀长期记忆。
- **它返回的不是片段，而是脉络**：不只是把像的内容召回出来，而是把关联、更新、冲突、依赖一起带回来，让答案更像推理结果，而不是检索拼接。
- **它保留的不是摘要，而是演进过程**：当前状态、历史状态、变化原因、支持证据都能并存，系统不容易在多轮刷新后把信息越记越薄。
- **它解决的不是 demo 问题，而是真实世界问题**：同名实体、多主体混杂、长周期演进、跨文档引用、why/how 问题，这些才是 AI 产品真正会遇到的复杂度。
- **它提供的不是“像对”，而是“可解释”**：回答可以回到原始证据、历史记录和关系链路，便于审计、调试，也更适合企业级 AI 场景。
- **它更像 AI 的持续认知层，而不是外挂缓存**：模型负责理解，记忆系统负责沉淀、维护和召回，这样 AI 才不只是一次性聪明，而是能持续积累能力。

一句更直接的话：InsightMemory 的核心优势，不是“记得更多”，而是记得更准、连得起来、讲得清楚、用得更久。

## 为什么它适合 AI 时代

AI 大火之后，应用层竞争会越来越集中在三个问题上：

- **能不能持续记住用户和任务上下文**：不是只记住上一轮对话，而是记住长期关系、规则、偏好、结论和变化历史。
- **能不能解释“为什么是这个答案”**：不是只给结论，而是把引用、证据、冲突和关联链条一起带回来。
- **能不能在复杂场景里持续工作**：多主体、同名实体、长时间演进、跨文档、跨格式输入，这些才是真实世界的 AI 输入。

如果说大模型是 AI 应用的大脑，那长期记忆系统更像 AI 应用的持续认知层。没有这层，很多 Agent 只能表现得
聪明一时；有了这层，系统才有机会变成真正可积累、可沉淀、可复用的 AI 产品。

## 解决什么问题

很多 LLM 应用不能只依赖“把文本切块后做向量检索”。如果一个系统只能搜到“像”的文本，那它更像一次性搜索，
而不是一个真正能持续工作的 AI 记忆系统。

长期记忆的核心难点，不是能不能搜到相似文本，而是系统能不能持续理解输入、组织记忆、维护关系，并在需要时
沿着这些关系找回真正有用的信息。

真正可用的记忆系统需要回答这些问题：

- 一段输入到底属于哪个稳定主体；
- 一条新记忆应该挂到哪个 `entity`，而不是混入全局文本池；
- 新事实是更新旧事实、补充旧事实、和旧事实冲突，还是应该与旧事实并存；
- 两条记忆之间是否存在支持、依赖、冲突、派生或相关关系；
- 同名但不同主体的记忆如何隔离；
- 当前状态问题和历史问题如何返回不同答案；
- 查询时如何不只召回相似文本，而是沿着 `memory graph` 找到关联记忆；
- 跨主体的外部约束如何参与 why/how 查询，同时不污染 entity 边界；
- 每个回答如何保留原始证据和引用。

InsightMemory 把这些能力封装成一个独立 HTTP 服务。LLM 负责语义理解、entity 判断、记忆抽取和关系识别；
PostgreSQL、pgvector 和检索索引负责持久化、召回和可审计的证据链。

## 相比常见记忆方案的优势

很多现有 memory 系统会把“记忆”简化成向量库、摘要缓存或 key-value profile。InsightMemory 的核心差异是：
它用 LLM 参与记忆理解和组织，同时把 entity identity、durable memory、evidence 和 memory graph 分开建模。

### 核心优势

- **自动判断记忆属于谁**：输入可以是对话、笔记、报告、日志或混合文档，系统会抽取其中的稳定主体，并把记忆挂到正确的 entity 上。
- **自动形成结构化长期记忆**：原始 observation 会沉淀为可更新、可并存、可追溯的 memory，而不是把每段原文都当作同等权重的 chunk。
- **自动构建记忆关系**：系统会识别 memory 之间的支持、更新、冲突、派生、依赖和相关关系，形成可维护的 memory graph。
- **支持关联记忆查询**：召回时不仅看语义相似度，还可以沿着 memory edge 扩展上下文，回答 why/how、current vs historical、依赖来源、冲突原因等问题。
- **保留证据链**：原始 observation append-only 保存，回答可以返回 citation，方便审计、调试和回放。
- **面向开放域泛化**：优先复用通用 entity 或 memory 或 edge 模型，而不是为单个场景写死 schema 或关键词规则。

### 相比纯向量库记忆

- 不只召回相似文本，而是先解析稳定主体，再从该主体的 memories 和关联 edge 中回答。
- 同名主体可以拆开，例如同一个名字下的项目、文档、规则、报告不会天然混在一起。
- 新输入可以被判断为更新、补充、并存或冲突，而不是简单追加一个新 chunk。
- 关联记忆可以参与召回，例如 blocker、上游依赖、外部 checklist、历史决策之间的关系可以一起进入答案。
- 回答可以带 observation citation，便于追溯原始证据。

### 相比摘要型长期记忆

- observation append-only，原始证据不会被覆盖。
- memory refresh 会保留旧细节并合并新增细节，避免补充规则覆盖当前规则。
- 历史记录可以作为独立 memory 并存，不会被当前状态简单吞掉。
- 查询“现在是什么”和“之前是什么”时，可以走不同召回路径。
- 查询“为什么变成这样”时，可以沿着更新、支持或冲突关系找回相关记忆。

### 相比 key-value 或 slot 型记忆

- 不强依赖预定义 `memory_type` 或固定 slot。
- 可处理项目、人物、文档、规则、市场观点和长历史记录等开放域主体。
- LLM 负责理解文本语义，数据库负责保存 identity、memory、evidence、relations 和 history。
- 遇到新领域时优先复用通用 entity 或 memory 或 edge 模型，而不是新增一套领域 schema。

### 相比单轮 Agent 记忆

- `memory_scope` 提供明确隔离，评估、用户、租户之间不会互相污染。
- 后台任务异步维护索引、关系图、entity profile 和 lifecycle，不把所有工作塞进前台请求。
- 关系图基于 memory-memory edge，可以解释为什么某个 blocker 会与外部 checklist、handbook 或 upstream service 相关。
- 评估矩阵覆盖高并发、跨格式、开放域、长文档和金融场景，目标是验证泛化能力，而不是只验证单个 demo。

## 适合的场景

- 需要长期记住用户、项目、文档、规则、分析结论或运行状态的 LLM 应用。
- 需要自动判断“这条记忆属于谁”的知识管理系统。
- 需要区分同名不同主体的企业知识库、Agent 记忆层或研究记录系统。
- 需要回答 current vs historical 问题的工作流。
- 需要基于关联记忆回答 why/how、影响范围、依赖来源、冲突原因的问题。
- 需要引用原始证据、支持审计和调试的企业应用。
- 需要在开放域输入中持续演进记忆，而不是只做一次性 RAG 检索的系统。

## 开发原则

- 优先使用 entity-centered memory，而不是只做原始文本 chunk retrieval。
- 保留原始证据和 citation。
- 记忆逻辑中避免关键词匹配。
- 不为了通过用例写定制化逻辑。
- prompt 示例必须和测试样本区分开。
- refresh 是补充型时，应保留旧细节并加入新细节。
